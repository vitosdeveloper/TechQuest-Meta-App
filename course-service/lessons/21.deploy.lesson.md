# 🚀 Implantando a Meta-App na Nuvem

Se você chegou até aqui, você construiu um sistema distribuído de alto calibre com NestJS, Fastify, Kafka, Clean Architecture, CQRS, GraphQL, Redis, e IA integrada.

Mas software rodando no `localhost` não gera valor real. Como empacotamos essa "besta" e colocamos em produção com Alta Disponibilidade?

## 1. O Problema do Docker Compose

No nosso ambiente de desenvolvimento, usamos o `docker-compose.yml`. Ele é ótimo para subir as dependências (Postgres, Kafka, Redis) e as APIs na sua máquina. Porém, o Compose **não tem orquestração real**:
- Se uma máquina da AWS morrer, o Docker Compose não "transfere" os containers para outra máquina sozinho.
- Ele não escala apenas o `user-service` automaticamente se a CPU dele bater 90%.

A solução da indústria é o **Kubernetes (K8s)**.

## 2. A Mágica do Kubernetes

No K8s, você tem um **Cluster** formado por vários nós (servidores). O Kubernetes distribui seus microserviços (agora chamados de *Pods*) de forma inteligente entre essas máquinas.

Em vez de escrever um `docker-compose.yml` gigante, nós separamos os serviços em *Manifestos YAML*.

```yaml
# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-gateway
spec:
  replicas: 3 # <-- Aqui está a mágica da alta disponibilidade
  template:
    spec:
      containers:
      - name: gateway
        image: minha-empresa/techquest-gateway:v1.2.0
```

Se um nó do servidor pegar fogo, o K8s percebe que o número de réplicas caiu para 2, e recria o terceiro Pod em um nó saudável em segundos.

## 3. Infraestrutura como Código (Terraform)

Como você cria o cluster Kubernetes na nuvem (como a AWS)? Clicando na interface web? **Não.**

Sêniores usam **Terraform**. Você declara que quer um cluster EKS na AWS com 3 máquinas, e o Terraform vai lá e cria tudo para você. Se amanhã você quiser mudar para o Google Cloud (GKE), basta mudar o provedor no arquivo e aplicar.

## 4. O Fluxo de GitOps (ArgoCD)

No passado, os desenvolvedores rodavam `kubectl apply -f arquivo.yaml` dos seus computadores. Hoje em dia usamos **GitOps**.

Temos um repositório no Github apenas com os YAMLs de configuração (ou arquivos Helm). O **ArgoCD** roda dentro do seu cluster Kubernetes, e fica "olhando" para esse repositório.
Se você alterar a versão da imagem do `course-service` no Github, o ArgoCD detecta a mudança e sincroniza o cluster para baixar a nova imagem automaticamente.
